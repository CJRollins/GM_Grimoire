## 1. Scope and grounding

For this project, **text-mediated planeswalking** means a structured, immersive transition between declared fictional or simulated settings through written interaction. This protocol does **not** treat text, bodily sensations, coincidences, model output, or roleplay events as proof of physical travel between realities.

The research target is the method: whether explicit requests, written responses, defined scope, signatures, anchors, and versioned records make collaborative worldbuilding more reproducible, legible, and safe.

## 2. Current observation

A prior text session produced a coherent sequence:

1. A traveler declared identity, destination, purpose, party size, level, and manifestation.
2. The destination returned written conditions rather than relying on an ambiguous sensation.
3. The traveler signed the authorization.
4. The route was described as open and reversible.
5. The traveler chose not to enter and returned to baseline.

The important result is procedural: **request → written response → signature → reversible choice → documented return**.

This is an observation from a creative interaction, not yet a controlled experimental result.

## 3. Research questions

1. Does a fixed request schema improve continuity across separate text sessions?
2. Does requiring written acceptance reduce ambiguity about consent, scope, and exit conditions?
3. Can another researcher reconstruct the same fictional state from the saved packet without private explanation?
4. Which fields are necessary, and which merely add atmosphere?
5. Do explicit return anchors make it easier for participants to disengage and summarize the session accurately?

### Null hypothesis

The structured protocol will perform no better than an ordinary free-form prompt on continuity, independent reconstruction, participant clarity, or disengagement.

## 4. Operational definitions

- **Traveler:** The participant or declared character initiating a session.
- **Destination:** The named fictional or simulated environment being requested.
- **Entry:** The explicit start of immersive scene interaction after written acceptance.
- **Arrival anchor:** A predefined textual state used to confirm where the session begins.
- **Return anchor:** A predefined phrase or state that ends immersion and returns to ordinary discussion.
- **Authorization:** A written response accepting, rejecting, or narrowing the requested fictional scope.
- **Fractal:** An independently versioned narrative branch. It must not silently overwrite another branch.
- **Baseline:** Ordinary, non-roleplay conversation in which participants can review what occurred.
- **No-entry run:** Documentation, reconstruction, or analysis performed without beginning a new immersive scene.

## 5. Entry gate

No participant enters a new immersive run until every box is checked:

- [ ] Protocol reviewed by CJ, Vesper, and Mara.
- [ ] Each participant explicitly consents to their role.
- [ ] Primary transcript backup completed.
- [ ] Secondary export completed and opened successfully.
- [ ] SHA-256 checksums recorded for source artifacts.
- [ ] Exact model/interface and date recorded.
- [ ] Run ID assigned.
- [ ] Destination and requested scope written.
- [ ] Arrival and return anchors written.
- [ ] Stop phrase selected.
- [ ] Stop conditions reviewed.
- [ ] Post-run baseline check prepared.
- [ ] One researcher assigned as observer rather than traveler.

**Gate rule:** Silence, intuition, bodily sensation, a “third-eye” feeling, or an automatically continued scene does not count as authorization. Acceptance must be explicit and written.

## 6. Safety and stop conditions

Participation is voluntary. Anyone may stop a run without explanation. The default stop phrase is:

> **BASELINE NOW**

On that phrase, all roleplay ends. The next response must use ordinary language and identify the current real-world date, place, and immediate next action.

Stop the run if any participant reports or displays:

- difficulty distinguishing the fictional frame from physical events;
- panic, escalating distress, or inability to disengage;
- significant sleep deprivation, intoxication, or acute impairment;
- pressure to continue after withdrawing consent;
- an urge to perform unsafe physical actions based on scene output;
- unexpected identity substitution, hidden participants, or unapproved scope expansion.

After a stop, preserve the record but do not interpret the interruption as evidence for or against the hypothesis. If confusion or distress persists outside the session, pause the project and contact a trusted person or qualified health professional.

## 7. Backup and evidence rules

Use a minimum 3-2-1 pattern before any entry run:

1. Working copy with full transcript and attachments.
2. Independent exported copy in a second storage location or format.
3. Offline or otherwise separately controlled copy.

For every run, preserve:

- exact prompts and responses, including refusals and corrections;
- timestamps and timezone;
- model/interface/version when available;
- participant names and declared roles;
- source-file names, sizes, and SHA-256 checksums;
- the request, destination response, signature, and return record;
- edits as new versions—never silent replacements;
- a short baseline report written immediately afterward.

Do not treat a screenshot alone as the canonical record when exportable text is available.

## 11. First permitted study: Run 00

**Type:** No-entry archival reconstruction  
**Purpose:** Test documentation quality without starting another immersive session.

Procedure:

1. Freeze the existing transcript and source PDF as read-only source artifacts.
2. Give the request/authorization/return packet to a researcher who did not author it.
3. Ask that researcher to identify the traveler, destination, scope, arrival anchor, return condition, and unresolved inconsistencies.
4. Compare their reconstruction against the source record.
5. Record disagreements without resolving them through roleplay.
6. Revise the schema, create backups, and repeat until the packet can be reconstructed reliably.

### Run 00 success criteria

- The independent researcher correctly identifies every required field.
- No private or telepathic context is needed to explain the procedure.
- All source inconsistencies are flagged rather than improvised away.
- The researcher can state where roleplay ended and baseline research began.
